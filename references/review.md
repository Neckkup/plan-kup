# ตรวจทานก่อนส่ง

ตรวจด้วยมุมมองของ tech lead ที่ต้องรับงานนี้ไปทำจริง และของลูกค้าที่ต้องเซ็นรับขอบเขต อย่าตรวจแค่ว่า "ถูกต้อง" ให้ถามว่า "ถ้าใช้ชุดนี้เริ่ม dev พรุ่งนี้ จะมีอะไรพัง"

## script ตรวจให้แล้ว (รัน `features.py check`)
- feature id ซ้ำ, priority ผิดรูปแบบ
- ฟีเจอร์อยู่เฟสก่อนสิ่งที่มันพึ่ง (`dependsOn`)
- ชื่อฟีเจอร์ซ้ำกันข้ามหมวดแต่ priority ต่างกัน
- ฟีเจอร์ MVP ที่มี UI แต่ไม่มีหน้าจอ (หน้าจอ `drawn: false` นับว่ามี)
- หน้าจอที่ไม่มีฟีเจอร์ MVP หรือ P1 อยู่เลย และหน้าจอที่มี MVP ปนกับเฟสหลัง
- คำถามที่ไม่มี owner
- หน้าจอที่ไม่มีฟีเจอร์ไหนอ้างถึง
- `affects` ของคำถามที่อ้าง feature id ที่ไม่มีอยู่
- MVP เกิน `mvpBudget`

## ต้องตรวจเอง
1. **ข้อความขัดกับ priority** เช่น lead ของหมวดหรือ desc เขียนว่า "แนะนำให้ย้ายขึ้น Phase 1" แต่ priority ยังเป็น L หรือหมวดเขียนว่า "ตามหลัง MVP ได้" แต่ข้างในมี M
2. **เรื่องเดียวกันที่ใช้ชื่อต่างกัน** script จับได้แค่ชื่อที่เหมือนกันเป๊ะ ให้ดูความหมาย เช่น "Maintenance schedule" กับ "Parts life tracker", "Points for registering" กับ "Earn points"
3. **dependency ที่ไม่ได้ใส่** ฟีเจอร์ที่ใช้แต้ม, ประกัน, หรือการตั้งค่าหลังบ้าน ต้องพึ่งของพวกนั้น ให้ใส่ `dependsOn` แล้วรัน check ใหม่
4. **back office ครบไหม** ทุกอย่างที่ลูกค้าทำได้ ต้องมีคนหลังบ้านจัดการได้ (ออเดอร์ → จัดการออเดอร์, คืนสินค้า → อนุมัติการคืน, คูปอง → สร้างคูปอง)
5. **brief ครบไหม** ทุกข้อใน brief ของลูกค้าอยู่ใน feature list
6. **หน้าจอกดได้ไหม** ทุก board มี `is_interactive: true` และ flow หลักกดต่อกันจนจบได้
7. **ภาษา** ข้อความบนหน้าจอตรงกับภาษาที่ผู้ใช้เลือก
8. **ตัวเลขที่แต่งขึ้น** ราคา สเปก และเงื่อนไขต้องมาจากแหล่งจริง หรือเป็น `[วงเล็บ]` ส่วนข้อมูลตัวอย่างต้องเขียนในโน้ตว่าเป็นตัวอย่าง
9. **คำถามที่ยังเปิด** แต่ละข้อบอกว่าใครต้องตอบ และถ้าคำตอบเปลี่ยนจะกระทบฟีเจอร์ไหน
10. **ของที่ต้องรอคิว** (⏱ ใน checklist) มีวันที่ต้องเริ่มกำกับ เป็นวันที่จริง
11. **งานแฝงที่ไม่มีใครเขียน** เช่น migration ของข้อมูลเดิม, ภาษี, การจัดส่ง, อีเมลแจ้งเตือน, webhook, job ตั้งเวลา
12. **state ระหว่างหน้าจอ** flow ที่แยกทางหรือวนกลับยังสมเหตุสมผลไหม (เลื่อนนัดแล้วต้องไม่จ่ายมัดจำซ้ำ)
13. **data-model.md** ละเอียดพอให้ dev เขียน schema ได้ไหม และต่อยอดจาก schema เดิมหรือเปล่า
14. **การตัดสินใจที่มีทางเลือก** มี `options` ที่เทียบข้อดีข้อเสียแล้ว ไม่ใช่แค่เหตุผลบรรทัดเดียว
15. **MVP เกิน budget** มีข้อเสนอตัดที่ชัดเจน และ assumptions อยู่ในคำตอบสุดท้าย
