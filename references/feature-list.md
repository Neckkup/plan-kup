2. นิยาม priority

## 1. Schema ของ features.json

```json

  "title": "Realmed App and Web: Feature List",
```

| field | บังคับ | ความหมาย |
|---|---|---|
| `id` | ใช่ | ไม่ซ้ำ ตัวพิมพ์เล็กคั่นด้วย `-` ใช้อ้างใน `dependsOn` และ `affects` |
| `pr` | ใช่ (ยกเว้น `status: "exists"`) | `M` / `P1` / `P2` / `L` |
| `screens` | — | รหัสหน้าจอใน `screens` ใช้ `"all"` ได้สำหรับข้อที่ครอบทุกหน้า |
| `ui` | — | ค่าเริ่มต้น `true` ให้ใส่ `false` สำหรับงานหลังบ้านที่ไม่มีหน้าจอ (security, webhook, SEO redirect) เพื่อไม่ให้ check เตือนว่าไม่มีหน้าจอ |
| `size` | — | `S` (≤ 2 วัน) = 1 แต้ม, `M` (≤ 1 สัปดาห์) = 3 แต้ม, `L` (> 1 สัปดาห์) = 8 แต้ม ไม่ใส่จะนับเป็น `M` |
| `dependsOn` | — | feature id ที่ต้องมีก่อน |
| `seen` | — | เห็นในแอปอ้างอิงไหน (เมื่อฟีเจอร์มาจากการดูคู่แข่ง) |
| `status` | — | `new` (ค่าเริ่มต้น) หรือ `exists` เมื่อมีในโค้ดแล้ว ข้อที่ exists ไม่ต้องใส่ `pr`, แสดงเป็น "มีแล้ว" และไม่นับใน budget |
| `screens.<รหัส>.drawn` | — | `false` = วางแผนไว้แต่ยังไม่ได้วาดบน canvas (ไม่ต้องมี `file`) |
| `mvpBudget` | — | ดูหัวข้อ "สูตร budget" ด้านล่าง |
| `decisions[].options` | — | ทางเลือกที่เทียบแล้ว `[{name, pros, cons}]` ใส่เมื่อเรื่องนั้นมีทางเลือกจริง |
| `assumptions` | — | สิ่งที่สมมติเองเพราะถามผู้ใช้ไม่ได้ แสดงใน decisions.md |

ถ้าใส่ `phases` ชื่อ priority จะใช้ค่าที่ใส่ ถ้าไม่ใส่จะใช้ MVP / Phase 1 / Phase 2 / Later เมื่อโปรเจกต์เองชื่อ "Phase 2" อยู่แล้ว ให้ตั้งชื่อใหม่ไม่ให้สับสน เช่น `"P1": "หลังเปิดตัว"`, `"P2": "Integration"`

### สูตร budget

ใส่กรอบเวลากับขนาดทีม แล้วให้ script คำนวณ:

```json
"mvpBudget": { "weeks": 8, "devs": 2 }
```

budget = สัปดาห์ × จำนวน dev × 3 แต้ม × (1 − 20%)

- 3 แต้มต่อคนต่อสัปดาห์ = ขนาด M หนึ่งข้อ (≤ 1 สัปดาห์)
- หัก 20% สำหรับงานที่ไม่ใช่ฟีเจอร์: setup, ออกแบบ, QA/UAT, deploy, รอ app review
- ปรับได้: `"overhead": 0.3` (ทีมใหม่หรือ integration เยอะ), `"pointsPerDevWeek": 4` (ทีมคุ้นกับ stack)
- นับเฉพาะ dev ที่เขียนโค้ด ไม่นับ PM หรือ designer
- ถ้ารู้ตัวเลขเองแล้วใส่ตรง ๆ ได้: `{"points": 38}` หรือ `{"count": 25}`

## 2. นิยาม priority

| รหัส | ความหมาย | ตัดสินอย่างไร |
|---|---|---|
| `M` MVP | release แรก | ถ้าไม่มีแล้วเปิดใช้งานไม่ได้ หรือผิดกฎหมาย/กฎ store หรือทำให้เป้าหมายหลักของ brief ไม่เกิด |
| `P1` | ส่วนที่เหลือของระบบหลัก | ลูกค้าคาดหวัง แต่เปิดตัวไปก่อนแล้วตามมาได้ |
| `P2` | AI, integration ที่ต้องรอคนนอก | ขึ้นกับ API, การอนุมัติ หรือข้อมูลที่ยังไม่มี |
| `L` Later | หลังเปิดตัว | มีก็ดี หรือยังไม่รู้ว่าคุ้มไหม |

ถามตัวเองทุกข้อที่ใส่ `M`: "ถ้าตัดข้อนี้ทิ้ง วันเปิดตัวยังไปได้ไหม" ถ้าไปได้ก็ไม่ใช่ MVP

## 3. วิธีเขียนแต่ละข้อ

- `name` เป็นคำนามสั้น ๆ ที่ลูกค้าอ่านเข้าใจ ไม่ใช่ชื่อ endpoint
- `desc` ใช้ 1–2 ประโยค บอกว่าผู้ใช้ทำอะไรได้ ใส่ตัวเลขหรือตัวอย่างจริงเมื่อมี (เช่น "ประกัน 3 ปีสำหรับเครื่องผลิตออกซิเจน")
- หัวหมวดตามด้วย `lead` 1 ประโยค บอกว่าหมวดนี้มีไว้ทำไม
- เรียงข้อในหมวดตาม priority (M ก่อน) แล้วตามลำดับที่ผู้ใช้เจอ

## 4. หมวดมาตรฐาน

เลือกหมวดที่เกี่ยวกับงาน ตัดหมวดที่ไม่เกี่ยว และเพิ่มหมวดเฉพาะธุรกิจ (เช่น ลงทะเบียนประกัน, งานซ่อม, เช่า):

1. บัญชีและการเข้าสู่ระบบ
2. (หมวดเฉพาะธุรกิจที่เป็นจุดขายหลัก ไว้ต้น ๆ)
3. แคตตาล็อก, ค้นหา, หน้าสินค้า
4. ตะกร้า, checkout, ชำระเงิน
5. ออเดอร์, จัดส่ง, คืนสินค้า
6. แต้มและโปรโมชัน
7. การแจ้งเตือน
8. ช่วยเหลือ, แชต, สาขา
9. หลายร้าน/หลายแบรนด์, ตัวแทนขาย (ถ้ามี)
10. Back office
11. Integration และ AI
12. ความเป็นส่วนตัว, กฎหมาย, กฎ app store
13. Accessibility, ภาษา, คุณภาพ
14. ไอเดียจากแอปอ้างอิง (ถ้าทำ research คู่แข่ง)

## 5. ฟีเจอร์ที่มักถูกลืม

ไล่ดูรายการนี้ทุกครั้ง ข้อไหนเกี่ยวกับงานให้ใส่:

**กฎ store และกฎหมาย (มักเป็น M)**
- ลบบัญชีได้เองในแอป (Apple และ Google บังคับ)
- Sign in with Apple ถ้ามี social login อื่นบน iOS
- PDPA: privacy notice, consent แยกเรื่อง marketing, สิทธิ์ขอดู/ลบข้อมูล, cookie banner บนเว็บ
- ใบอนุญาตโฆษณา (เช่น เลข ฆพ. สำหรับเครื่องมือแพทย์, อย. สำหรับอาหารเสริม)
- หน้า terms และนโยบายคืนสินค้า

**ไทยโดยเฉพาะ**
- กรอกที่อยู่จากรหัสไปรษณีย์
- ใบกำกับภาษีเต็มรูป (ชื่อบริษัท, เลขผู้เสียภาษี, สาขา)
- PromptPay QR, mobile banking, เก็บเงินปลายทาง
- LINE Login และ LINE OA สำหรับแจ้งเตือน
- เบอร์โทรพร้อม OTP สำหรับผูกกับข้อมูลลูกค้าเดิม

**ระบบหลังบ้านที่มองไม่เห็นในหน้าจอลูกค้า**
- นำเข้าข้อมูลสินค้าและลูกค้าเดิม, รวมบัญชีที่ซ้ำ
- redirect URL เดิมทั้งหมด (ถ้ามีเว็บเดิม)
- roles และ permissions, audit log
- จัดการเนื้อหา (banner, FAQ) ได้โดยไม่ต้องพึ่ง dev
- analytics funnel, crash/error reporting, บังคับอัปเดตแอปรุ่นเก่า
- security: เข้ารหัส, backup, 2FA ของ admin
