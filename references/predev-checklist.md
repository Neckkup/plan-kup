# Checklist ก่อนเริ่ม dev

ไล่ทีละข้อ แต่ละข้อได้ผลเป็นอย่างใดอย่างหนึ่ง: **ตัดสินแล้ว** (ลง `decisions`) / **ยังเปิด** (ลง `questions` พร้อม `affects` และ `owner`) / **ไม่เกี่ยว** (ข้าม)

ข้อที่มี ⏱ มีระยะรอคิว ให้ใส่ `due` ว่าต้องเริ่มภายในเมื่อไหร่

## A. ขอบเขต
- [ ] ลูกค้ารับรายการ MVP และกรอบเวลาแล้ว (ใครเซ็น วันไหน)
- [ ] MVP ไม่เกิน `mvpBudget` ถ้าเกินต้องตกลงว่าจะตัดอะไร
- [ ] ทุกข้อใน brief ของลูกค้าอยู่ใน feature list (จะเป็น Later ก็ได้)
- [ ] เกณฑ์ว่า "เสร็จ" ของ MVP (ใครทดสอบ, ทดสอบบนอุปกรณ์อะไร)

## B. Data model (เปลี่ยนทีหลังต้องรื้อ)
- [ ] entity หลักและความสัมพันธ์ (ลูกค้า, สินค้า/variant, ออเดอร์, ฯลฯ)
- [ ] multi-tenant / หลายร้าน / หลายแบรนด์: ข้อมูลไหนผูกกับร้าน, ใครเห็นอะไร
- [ ] ตัวตนลูกค้า: ใช้อะไรเป็น key (เบอร์, อีเมล, LINE ID) และวิธีรวมบัญชีซ้ำ
- [ ] การนำเข้าข้อมูลเดิม: จากระบบไหน, รูปแบบอะไร, ปริมาณเท่าไหร่, ใครส่งให้
- [ ] สิ่งที่ต้องเผื่อไว้สำหรับเฟสหลัง (เช่น marketplace ผู้ขายภายนอก, การเช่า) โดยไม่ต้องสร้างวันนี้
- [ ] กฎที่มีผลกับข้อมูล: หนึ่ง serial มีเจ้าของคนเดียว, แต้มหมดอายุ, การคืนเงิน
- [ ] migration ของข้อมูลที่ใช้งานจริงอยู่ (ถ้ามีระบบเดิม) เป็นฟีเจอร์ใน MVP ด้วย ไม่ใช่งานแฝง

ผลของหัวข้อนี้คือไฟล์ `data-model.md` แบบนี้ (ใช้ภาษาของ schema เดิม ถ้าไม่มีใช้ตารางก็ได้):

```markdown
# Data model

## ของเดิมที่ใช้ต่อ
User, Product, Order, OrderItem (prisma/schema.prisma)

## เพิ่ม
model Subscription {
  id            String   @id @default(cuid())
  userId        String                      // → User
  productId     String                      // → Product
  interval      Interval                    // WEEKLY | BIWEEKLY | MONTHLY
  status        SubStatus                   // ACTIVE | PAUSED | CANCELED
  nextChargeAt  DateTime
  stripeSubId   String?  @unique            // ถ้าเลือก Stripe Billing (ดู decisions)
}

## แก้ของเดิม
Order: + subscriptionId String?, + refundedCents Int @default(0)

## กฎ
- แต้มเก็บเป็น ledger (เพิ่ม/ลด แยกแถว) ไม่เก็บยอดคงเหลือเป็นค่าเดียว
- คืนสินค้า → ลบแต้มที่ได้จากออเดอร์นั้น และคืนแต้มที่ใช้ไป

## Migration
- เพิ่ม column ใหม่เป็น nullable ก่อน backfill แล้วค่อยตั้ง NOT NULL
```

## C. Stack และโครงสร้าง

ข้อที่มีทางเลือกจริงให้ใส่ `options` ใน decisions อย่างน้อย 2 ทาง พร้อมข้อดีข้อเสีย
- [ ] แอป: cross-platform ตัวเดียว หรือ native แยก
- [ ] เว็บ: framework, SSR สำหรับ SEO หรือไม่
- [ ] backend, database, hosting, ที่เก็บไฟล์และรูป
- [ ] auth: ทำเอง หรือใช้บริการ
- [ ] สภาพแวดล้อม dev / staging / production และ CI/CD (ใช้ skill `deploy-kup` ต่อได้)

## D. ผู้ให้บริการภายนอก ⏱
- [ ] Payment gateway: เปิดบัญชีแล้วหรือยัง, รองรับวิธีจ่ายที่ต้องใช้ไหม (บัตร, PromptPay, ผ่อน, ตัดรายเดือน)
- [ ] subscription หรือตัดเงินซ้ำ: ใช้ระบบของ gateway (เช่น Stripe Billing) หรือเขียนเอง ต้องเทียบ `options`
- [ ] ภาษีและการจัดส่ง: คำนวณภาษีอย่างไร (VAT, sales tax), ค่าส่งตามพื้นที่, ผู้ให้บริการขนส่ง
- [ ] LINE Login / LINE OA, SMS OTP, อีเมล
- [ ] ขนส่ง: มี API สถานะไหม หรือกรอกเลข tracking เอง
- [ ] Apple Developer และ Google Play account ของลูกค้า (ชื่อบริษัทต้องตรง, ใช้เวลาหลายวัน) ⏱
- [ ] Meta (Messenger, IG) app review, TikTok API ⏱ หลายสัปดาห์
- [ ] ระบบบัญชี, CRM, ERP ที่ต้องเชื่อม: ชื่อระบบ, มี API ไหม, ใครให้สิทธิ์
- [ ] สิ่งที่ต้องผลิตจริง เช่น QR บนกล่อง, ป้าย, บัตร ⏱ ต้องตัดสินก่อนสั่งพิมพ์

## E. กฎหมายและนโยบาย
- [ ] PDPA: privacy notice, consent, ผู้รับผิดชอบคำขอลบข้อมูล
- [ ] ข้อความ consent พิเศษ (เช่น ให้ AI วิเคราะห์แชต) ผ่านทนายแล้วหรือยัง
- [ ] ใบอนุญาตโฆษณาสินค้าที่ต้องมี (ฆพ., อย.) มีครบทุกสินค้าไหม
- [ ] terms, นโยบายคืนสินค้า, เงื่อนไขการเช่า: ใครเขียน

## F. เนื้อหาและการย้ายระบบ
- [ ] ใครส่งรูป ข้อความ และข้อมูลสินค้า ภายในวันไหน
- [ ] ภาษา: ไทยอย่างเดียว หรือไทย + อังกฤษ ใครแปล
- [ ] URL เดิมทั้งหมดสำหรับ redirect
- [ ] แผนวันย้ายระบบ: ปิดเว็บเดิมเมื่อไหร่, ทำ DNS อย่างไร

## G. คนและการทำงาน
- [ ] roles ในหลังบ้าน (admin, ผู้จัดการร้าน, ตัวแทนขาย, ช่าง, คนทำเนื้อหา) และสิทธิ์ของแต่ละ role
- [ ] ใครฝั่งลูกค้าเป็นคนตัดสินใจ และใครอนุมัติงานรายวัน (เช่น ตรวจใบเสร็จ)
- [ ] ช่องทางและรอบการรีวิวงานกับลูกค้า
